# Исправление эксперимента с вытеснением

В первой попытке оба Pod остались Running. Сообщение scheduler у hh-high о выборе одной жертвы не доказывает вытеснение hh-low. Событий другого namespace в переданном выводе нет, поэтому конкретная другая жертва не установлена.

В исходном сценарии hh-high имел приоритет 1000, hh-low — 100. Поэтому обычные Pod с приоритетом 0 тоже могли быть жертвами hh-high. Сценарий не изолировал выбор жертвы.

Изменения:

- Новые классы hh-lab-low-v2=-1000 и hh-lab-high-v2=-500. Высокий приоритет здесь означает высокий относительно тестового hh-low. Обычный приоритет 0 выше обоих.
- Проверка перед опытом: на узле нет других активных Pod с приоритетом ниже -500.
- Подтверждение, что запрос hh-high не помещается в свободный CPU до его запуска.
- Подтверждение вытеснения по UID жертвы: событие Preempted либо условие DisruptionTarget/PreemptionByScheduler; старые события одноимённых Pod не засчитываются.
- Успех требует завершения/удаления исходного hh-low и запуска hh-high. Одного сообщения о выборе возможной жертвы недостаточно.
- Ожидание доставки событий, поскольку они записываются асинхронно.
- Сохранение состояния всех namespace до/после опыта для диагностики.
- Прежняя папка scheduling переносится в scheduling-attempts/ перед новой попыткой.
- Ожидание готовности статуса ResourceQuota перед проверкой её действия.

Локально прошли 11 тестов: 5 проверок обработки данных и 6 проверок сценария/доказательств вытеснения. Kubernetes в среде подготовки не запускался; фактический результат нужно получить на компьютере студентки.

После распаковки исправления в корень существующего проекта:

```bash
python -m unittest discover -s k8s/tests -v
python -m k8s.lab scheduling
```

Пересобирать образ или повторять setup, memory, storage и pipeline не требуется: изменён runner на компьютере и определения тестовых PriorityClass. Вычислительная программа в образе осталась прежней.
